# Tessellation: Height Map

The next two chapters follow learnopengl's guest articles on **tessellation**: letting the GPU itself subdivide a coarse
mesh into a fine one. To see why that is worth having, this first chapter does it the old way: a landscape built entirely
on the CPU, one vertex for every pixel of a height map, sent to the GPU as one big, dense mesh. The next chapter,
*Tessellation*, draws the same landscape from a mesh of only a few hundred vertices and lets the tessellation stages add
the detail – and adapt it to the distance from the camera.

Nothing in this chapter is new for the GPU: a vertex buffer, an index buffer, triangle strips and a fragment shader that
colours by height. It works the same way in every API; the interesting part is the mesh and what it costs.

## Height maps

A **height map** is a grey-scale image read as a landscape: every pixel is a point on a grid, and its grey value says how
high the ground is there – black is low, white is high. Height maps are how terrain is usually stored and edited: an
artist paints hills and valleys, or a program generates them from noise, or they come from real elevation data.
learnopengl uses a large map of real terrain, 2.6 thousand pixels on a side. The course uses its own, smaller map –
`heightmap.png`, 256 × 256 pixels with one 8-bit grey channel, generated by the course's script `textures/make_guest.py`
from seeded fractal noise: rolling hills, a ridge of peaks along the image's top edge, a river valley from the left edge
down to the bottom edge, and a lake at the bottom right. The smaller size keeps the grid at 65,536 vertices, which the
built-in simulator can draw.

The camera looks at the whole landscape from the front and above: from (0, 190, 290), turned 35° down, with a far plane
of 1000 (learnopengl starts at a point over its much larger map). The fragment shader colours every point by its height.

:::opengl
The project is a plain OpenGL 3.3 program: `main.cpp`, the course's `Shader` class, `cpuheight.vs` / `.fs`
(learnopengl's `8.3.cpuheight` shaders) and `heightmap.png`. The start opens the window and clears it; there is nothing to
draw yet.
:::
:::vulkan
The project is a plain Vulkan program with a pipeline for `shaders/cpuheight.vert` / `.frag`, the camera's matrices in a
uniform buffer and the model matrix as a push constant. The start's `loadHeightMap()` is empty, and `vertexBuffer` and
`indexBuffer` stay `VK_NULL_HANDLE` – Vulkan cannot create a buffer of size 0, and destroying a null handle does nothing.
`createVertexBuffer()` and `createIndexBuffer()` are the *Model Loading* chapters' staging-buffer functions; the tasks
call them once the data exists. The height map is only read on the CPU, so no texture is created for it.
:::
:::d3d12
The project is a plain Direct3D 12 program with a pipeline state for `cpuheight.hlsl`, the camera's matrices in a constant
buffer and an empty `LoadAssets` section for the terrain. A Windows program has no console, so where learnopengl prints
with `std::cout`, the course writes to the debugger's output window with `OutputDebugStringA` (after `snprintf` into a
buffer).
:::

The `// TODO:` comments mark where your code goes; **Build & run** (Ctrl+Enter) compiles the program and runs it in the
built-in simulator: an empty, dark window.

## Loading the height map

stb_image loads the map; the last argument 0 asks for the file's own number of channels – 1 here, a grey image. Unlike
the textures of the earlier chapters, the image is not flipped: its first row is the top of the image, and the course puts
that row at the back of the terrain, so that seen from above the terrain looks like the image. (learnopengl's two terrain
demos differ in both the flip and the orientation; the course uses the same orientation in both chapters, so they show the
same landscape the same way round.)

:::opengl
```cpp
    int width, height, nrChannels;
    unsigned char *data = stbi_load("heightmap.png", &width, &height, &nrChannels, 0);
    if (data)
    {
        std::cout << "Loaded heightmap of size " << height << " x " << width << std::endl;
    }
    else
    {
        std::cout << "Failed to load texture" << std::endl;
        return -1;
    }
```
:::
:::vulkan
`loadHeightMap()` loads `textures/heightmap.png` with `stbi_load(path, &width, &height, &nrChannels, 0)`, prints the
size, and throws a `std::runtime_error` if the file can't be loaded.
:::
:::d3d12
`LoadAssets` calls `stbi_load` with 0 channels, and writes the size to the debugger's output:

```cpp
        snprintf(text, sizeof(text), "Loaded heightmap of size %d x %d\n", height, width);
        OutputDebugStringA(text);
```
:::

Now do the first task, **load-heightmap**. Nothing is drawn yet; the program reports a map of 256 × 256.

## One vertex per pixel

Every pixel becomes a vertex. Its column `j` gives the x coordinate and its row `i` the z coordinate, both centred
around the origin, so the grid runs from −128 to 127 in x and z. The pixel's grey value, 0 to 255, gives the height:
learnopengl scales it by `yScale = 64 / 256` and shifts it down by `yShift = 16`, so the heights range from −16 to
about 48:

:::opengl
```cpp
    std::vector<float> vertices;
    float yScale = 64.0f / 256.0f, yShift = 16.0f; // apply a scale and a shift to the height data
    unsigned bytePerPixel = nrChannels;
    for (int i = 0; i < height; i++)
    {
        for (int j = 0; j < width; j++)
        {
            unsigned char* pixelOffset = data + (j + width * i) * bytePerPixel;
            unsigned char y = pixelOffset[0];

            // vertex: column j along x, row i along z (the image's top row at the back)
            vertices.push_back(-width / 2.0f + width * j / (float)width);   // vx
            vertices.push_back((int)y * yScale - yShift);                    // vy
            vertices.push_back(-height / 2.0f + height * i / (float)height); // vz
        }
    }
```

After the loop the image is freed with `stbi_image_free(data)`, and the vertices go into a VBO in a VAO with one
attribute: three floats at location 0.
:::
:::vulkan
```cpp
        for (int i = 0; i < height; i++) {
            for (int j = 0; j < width; j++) {
                unsigned char* pixelOffset = data + (j + width * i) * bytePerPixel;
                unsigned char y = pixelOffset[0];

                // vertex: column j along x, row i along z (the image's top row at the back)
                Vertex vertex{};
                vertex.pos.x = -width / 2.0f + width * j / (float) width;   // vx
                vertex.pos.y = (int) y * yScale - yShift;                    // vy
                vertex.pos.z = -height / 2.0f + height * i / (float) height; // vz
                vertices.push_back(vertex);
            }
        }
```

with `float yScale = 64.0f / 256.0f, yShift = 16.0f;` and `unsigned bytePerPixel = nrChannels;` before the loops.
`Vertex` is just `glm::vec3 pos` at location 0. After the loop the image is freed, and `createVertexBuffer()` copies the
global `vertices` into a device-local buffer.
:::
:::d3d12
The loop is learnopengl's: for each row `i` and column `j`, the pixel at `data + (j + width * i) * bytePerPixel`, and
three floats pushed into `std::vector<float> vertices` – `-width / 2.0f + width * j / (float)width`, `(int)y * yScale -
yShift` and `-height / 2.0f + height * i / (float)height`. After it the image is freed, and the vertices go into an
upload-heap buffer (`StrideInBytes = 3 * sizeof(float)`, input layout `POSITION` as `R32G32B32_FLOAT`).
:::

`bytePerPixel` is the number of channels: for a grey image every pixel is one byte, for RGBA four, and the first byte is
the height either way. learnopengl's map is RGBA; with `nrChannels` from `stbi_load` the same loop reads both.

For a first look, the task draws the vertices as **points**.

:::opengl
`glDrawArrays(GL_POINTS, 0, (GLsizei)(vertices.size() / 3));` with the VAO bound.
:::
:::vulkan
For now the pipeline's topology is `VK_PRIMITIVE_TOPOLOGY_POINT_LIST`, and `recordCommandBuffer()` binds the vertex buffer
and calls `vkCmdDraw(commandBuffer, static_cast<uint32_t>(vertices.size()), 1, 0, 0)`. The vertex shader must also write
`gl_PointSize = 1.0;` – Vulkan takes the size of a point only from the shader (the strips task removes it again).
:::
:::d3d12
In Direct3D 12 the primitive topology has two parts: the pipeline state's `PrimitiveTopologyType` (point, line, triangle
or patch – what the rasterizer receives) and the command list's `IASetPrimitiveTopology` (list or strip – how the vertices
are put together). The start's pipeline state is made for points; the command list sets
`D3D_PRIMITIVE_TOPOLOGY_POINTLIST` and draws the vertices. A point is one pixel in Direct3D – there is no point size.
:::

Now do the second task, **vertices**. Build and run: the terrain appears as a cloud of 65,536 white points, dense on the
steep peaks at the back, with gaps between the rows in front.

## Triangle strips

To turn the points into a surface, neighbouring vertices are connected into triangles. A grid is the classic case for
**triangle strips**: a strip is a list of vertices in which every vertex after the first two makes a triangle with the
two before it. Zigzag between two neighbouring rows – one vertex from row `i`, then one from row `i + 1`, then the next
column – and each new vertex adds a triangle. A strip over 256 columns has 512 indices and 510 triangles; with a plain
triangle list the same triangles would need 1530 indices.

learnopengl builds one strip per pair of rows with three nested loops:

:::opengl
```cpp
    std::vector<unsigned int> indices;
    int rez = 1;
    for (int i = 0; i < height - 1; i += rez)
    {
        for (int j = 0; j < width; j += rez)
        {
            for (int k = 0; k < 2; k++)
            {
                indices.push_back(j + width * (i + k * rez));
            }
        }
    }
```

```cpp
    const int numStrips = (height - 1) / rez;
    const int numTrisPerStrip = (width / rez) * 2 - 2;
```

The indices go into `terrainIBO`, bound to `GL_ELEMENT_ARRAY_BUFFER` while the VAO is bound, so the VAO remembers it.

```quiz
Why is `terrainIBO` bound to `GL_ELEMENT_ARRAY_BUFFER` while `terrainVAO` is bound?
- [ ] Because `glBufferData` only works on a buffer bound inside a VAO
- [ ] Because element buffers must be created after the vertex buffer
- [ ] Because the strips are drawn from the VBO, not from the element buffer
- [x] Because the VAO records the element buffer bound while it is bound – binding the VAO later for drawing brings the indices with it
---
The element buffer binding is part of the VAO's state, unlike the `GL_ARRAY_BUFFER` binding, which is only recorded per attribute by `glVertexAttribPointer`.
```
:::
:::vulkan
The same loops fill the global `std::vector<uint32_t> indices` (`indices.push_back(j + width * (i + k * rez));` for
`i` over the rows but the last, `j` over the columns and `k` = 0, 1), with `numStrips = (height - 1) / rez` and
`numTrisPerStrip = (width / rez) * 2 - 2`. `createIndexBuffer()` uploads them; the index type is `VK_INDEX_TYPE_UINT32`,
because 65,536 vertices use up every 16-bit index value.

```quiz
Why does the terrain use 32-bit indices (`VK_INDEX_TYPE_UINT32`)?
- [ ] Because triangle strips require 32-bit indices
- [ ] Because 16-bit indices can't be uploaded with a staging buffer
- [x] Because the grid's 65,536 vertices use every 16-bit value up to 65,535 – the value primitive restart reserves – and one more column would overflow; 32-bit indices leave room
- [ ] Because the index buffer is larger than 64 KB
---
Larger terrain is split into tiles or uses 32-bit indices. Each index then takes 4 bytes instead of 2 – 522 KB for this terrain's 130,560 indices.
```
:::
:::d3d12
The same loops fill `std::vector<unsigned int> indices` (`indices.push_back(j + width * (i + k * rez));` for `i` over
the rows but the last, `j` over the columns and `k` = 0, 1), with learnopengl's counts kept in members:
`m_numStrips = (height - 1) / rez` and `m_numTrisPerStrip = (width / rez) * 2 - 2`. The indices go into an upload-heap
buffer with an index buffer view of format `DXGI_FORMAT_R32_UINT`.

```quiz
Why does the terrain's index buffer view use `DXGI_FORMAT_R32_UINT`?
- [ ] Because `DrawIndexedInstanced` only accepts 32-bit indices
- [x] Because the grid's 65,536 vertices use every 16-bit value up to 65,535 – the strip-cut value – and one more column would overflow; 32-bit indices leave room
- [ ] Because upload heaps can't hold 16-bit data
- [ ] Because the vertex buffer's stride is 12 bytes
---
Larger terrain is split into tiles or uses 32-bit indices. Each index then takes 4 bytes instead of 2 – 522 KB for this terrain's 130,560 indices.
```
:::

That makes 255 strips of 510 triangles – 130,050 triangles from 130,560 indices. learnopengl's `rez` would use only
every `rez`-th vertex, for a coarser mesh. With this map it only works for `rez = 1`: the strip counts `(height − 1) /
rez` and `(width / rez) · 2 − 2` only fit when `rez` divides both 255 and 256, and no number above 1 does. Level of
detail done properly – coarser where the terrain is far away – is what the next chapter's tessellation is for.

```quiz
How many indices does one strip over the 256 columns of two neighbouring rows have, and how many triangles?
- [x] 512 indices and 510 triangles: two per column, and every index after the first two adds a triangle
- [ ] 256 indices and 255 triangles
- [ ] 1530 indices and 510 triangles
- [ ] 512 indices and 256 triangles
---
That is `numTrisPerStrip = width · 2 − 2` = 510, drawn with `numTrisPerStrip + 2` = 512 indices. A triangle list would need three indices per triangle: 1530.
```

Now do the third task, **indices**. The picture doesn't change yet: the indices exist, but the draw still uses points.

## Drawing the strips

Each strip is a separate primitive: if the whole index buffer were drawn as one strip, the last vertex of one strip and
the first of the next would form long triangles across the terrain from one edge to the other. So learnopengl draws the
strips one by one, each with `numTrisPerStrip + 2` indices starting at its own place in the index buffer:

:::opengl
```cpp
        glBindVertexArray(terrainVAO);
        for (int strip = 0; strip < numStrips; strip++)
        {
            glDrawElements(GL_TRIANGLE_STRIP,   // primitive type
                           numTrisPerStrip + 2, // number of indices to render
                           GL_UNSIGNED_INT,     // index data type
                           (void*)(sizeof(unsigned int) * (numTrisPerStrip + 2) * strip)); // offset to starting index
        }
```

The last argument of `glDrawElements` is a *byte* offset into the element buffer, disguised as a pointer.
:::
:::vulkan
The pipeline's topology becomes `VK_PRIMITIVE_TOPOLOGY_TRIANGLE_STRIP`, and `recordCommandBuffer()` binds the index buffer
and draws the strips:

```cpp
        // draw mesh strip by strip: each strip starts (numTrisPerStrip + 2) indices after the one before
        for (int strip = 0; strip < numStrips; strip++) {
            vkCmdDrawIndexed(commandBuffer,
                             numTrisPerStrip + 2,                  // number of indices to render
                             1,                                    // one instance
                             (numTrisPerStrip + 2) * strip,        // the strip's first index
                             0, 0);
        }
```

`vkCmdDrawIndexed`'s `firstIndex` counts indices, where OpenGL's last argument is a byte offset. Culling stays off
(`VK_CULL_MODE_NONE`): the triangles of a strip alternate their winding.
:::
:::d3d12
The pipeline state's `PrimitiveTopologyType` becomes `D3D12_PRIMITIVE_TOPOLOGY_TYPE_TRIANGLE`, the command list sets
`D3D_PRIMITIVE_TOPOLOGY_TRIANGLESTRIP`, and the strips are drawn one by one:

```cpp
    for (int strip = 0; strip < m_numStrips; strip++)
    {
        m_commandList->DrawIndexedInstanced(m_numTrisPerStrip + 2,    // number of indices to render
            1,                                                       // one instance
            (m_numTrisPerStrip + 2) * strip,                         // offset to starting index
            0, 0);
    }
```

`StartIndexLocation`, the third argument, counts indices, where OpenGL's last argument is a byte offset. Culling stays
off (`D3D12_CULL_MODE_NONE`): the triangles of a strip alternate their winding.
:::

255 draw calls per frame for one terrain is wasteful. The usual alternative is **primitive restart**: put a special index
between the strips that tells the GPU "end this strip, start a new one", and draw everything with one call.
:::opengl
In OpenGL: `glEnable(GL_PRIMITIVE_RESTART)` with `glPrimitiveRestartIndex(0xFFFFFFFF)` (or, since 4.3,
`GL_PRIMITIVE_RESTART_FIXED_INDEX`, which always uses the largest value of the index type).
:::
:::vulkan
In Vulkan: `inputAssembly.primitiveRestartEnable = VK_TRUE` in the pipeline, and the index `0xFFFFFFFF` (for 32-bit
indices) after each strip.
:::
:::d3d12
In Direct3D 12 it is called the *strip-cut value*: `psoDesc.IBStripCutValue = D3D12_INDEX_BUFFER_STRIP_CUT_VALUE_0xFFFFFFFF`
in the pipeline state, and that index after each strip.
:::
A plain triangle list works too, at the cost of more indices. The course keeps learnopengl's loop, which shows the strips
most directly.

```quiz
Why does the program draw each strip separately instead of drawing all 130,560 indices as one triangle strip?
- [ ] Because a single draw call is limited to 65,536 indices
- [ ] Because the index buffer holds each strip in its own buffer
- [x] Because one long strip would join the end of each row pair to the start of the next with triangles stretched across the terrain
- [ ] Because triangle strips can only cover two rows of a grid
---
In a strip every new index makes a triangle with the two before it – also across the jump from one row pair to the next. Separate draws, or a primitive-restart index between the strips, end each strip where it should.
```

Now do the fourth task, **strips**. Build and run: the terrain is a solid white shape – the silhouette of the peaks
against the dark background, the front edge at the bottom. The fragment shader still writes white, so there is no
shading to see the hills by.

## Colouring by height

The vertex shader passes the height (`aPos.y`) on to the fragment shader. Shifting it up by 16 and dividing by 64 turns
the range −16 … 48 into a grey value from 0 to 1 – the height map's own grey, roughly:

:::opengl
```glsl
    float h = (Height + 16.0) / 64.0; // shift and scale the height into a grey value (0 .. 1)
    FragColor = vec4(h, h, h, 1.0);
```

(learnopengl's CPU shader divides by 32, which turns everything above height 16 white; its GPU shader divides by 64, as
the course does in both chapters.)
:::
:::vulkan
In `cpuheight.frag`: `float h = (Height + 16.0) / 64.0; outColor = vec4(h, h, h, 1.0);`. (learnopengl's CPU shader divides
by 32, which turns everything above height 16 white; its GPU shader divides by 64, as the course does in both chapters.)
:::
:::d3d12
In `cpuheight.hlsl`'s pixel shader: `float h = (input.height + 16.0f) / 64.0f;` returned as `float4(h, h, h, 1.0f)`.
(learnopengl's CPU shader divides by 32, which turns everything above height 16 white; its GPU shader divides by 64, as
the course does in both chapters.)
:::

Now do the last task, **height-colour**. Build and run: the landscape in grey – bright peaks along the back, the dark
river valley winding to the front, the lake almost as dark as the background.

```quiz
A vertex's pixel in the height map has the grey value 128. Which grey does the fragment shader give it?
- [ ] 128 / 255 ≈ 0.50, the same value
- [x] Height 128 · 64/256 − 16 = 16, and (16 + 16) / 64 = 0.5
- [ ] Height 128 − 16 = 112, which is clamped to 1.0
- [ ] (128 + 16) / 64 = 2.25, clamped to 1.0
---
The vertex loop scales the 0–255 value to −16 … 47.75; the shader undoes the shift and divides by the range of 64. The result is the map's own grey, up to the rounding of the heights.
```

## The cost of a dense mesh

The terrain works, but look at what it costs. 65,536 vertices and 130,050 triangles for a 256 × 256 map – and
learnopengl's 2.6 k map has about 7 million vertices. Every vertex is stored in GPU memory, transformed by the vertex
shader every frame, and every triangle set up and rasterised, whether it lies right in front of the camera or far away,
where it covers a fraction of a pixel. The detail is fixed when the mesh is built: to show more of it near the camera you
need a denser mesh everywhere; to save work far away you need several meshes and a CPU that picks between them.

Tessellation turns this around. The CPU sends a coarse grid of *patches*, and the GPU subdivides each patch while drawing
– as finely as the shader decides, patch by patch, frame by frame. The heights are read from the height map as a
**texture** in the shader instead of being baked into the vertices. That is the next chapter.

```quiz
What does tessellation change compared with this chapter's terrain?
- [x] The CPU sends a coarse grid of patches, and the GPU subdivides each patch while drawing – as finely as a shader decides, so detail can follow the distance to the camera
- [ ] The CPU sends the same 65,536 vertices, but the GPU draws them as points
- [ ] The height map is no longer needed, because the GPU generates the heights
- [ ] The vertices are computed once on the GPU and then stored as a dense mesh
---
The heights still come from the height map – read as a texture in the shader. What changes is where and how finely the mesh is made: on the GPU, every frame, patch by patch.
```
