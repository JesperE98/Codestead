# Сеть

Почти всё, что делает компьютер с Linux, связано с общением с другими
компьютерами: загрузка обновлений, открытие веб-страниц, вход на серверы.
Когда что-то идёт не так, лучшие инструменты для поиска причины есть именно
в терминале. В этой главе вы научитесь узнавать свой адрес, проверять
соединения, искать имена, смотреть, какие службы запущены, скачивать что-то
из интернета и входить на другой компьютер по SSH.

Симулированный компьютер находится в небольшой домашней сети:

| Компьютер | Адрес | Что это |
|---|---|---|
| Ваш компьютер ({{hostname}}) | `192.168.1.42` | Здесь вы сейчас находитесь |
| Роутер (шлюз) | `192.168.1.1` | Выход в интернет |
| Сервер | `192.168.1.10` | Другой компьютер с Linux, на который можно войти |

За роутером находится «интернет», в котором есть, среди прочего,
`example.com`, `linux.org` и `archlinux.org`.

## IP-адреса

У каждого компьютера в сети есть **IP-адрес**. Адрес IPv4 – это четыре числа
от 0 до 255, например `192.168.1.42`. Адреса, начинающиеся с `192.168.`,
`10.` или `172.16.`–`172.31.`, – **частные**: они используются только внутри
локальных сетей и никогда не видны в интернете.

Команда, показывающая адреса компьютера, – `ip` (из пакета *iproute2*).
`ip addr` можно сократить до `ip a`:

```sh
ip a
```

Вы увидите два **интерфейса** (сетевые карты):

- `lo` – *loopback*, «ненастоящая» карта, через которую компьютер общается
  сам с собой.
- `enp0s3` – настоящая сетевая карта. Раньше карты назывались `eth0`, а
  беспроводные часто называются как-нибудь вроде `wlan0` или `wlp2s0`.

Строка `inet 192.168.1.42/24` – это ваш IPv4-адрес. `link/ether` – это
**MAC-адрес** карты, зашитый в оборудование, а `state UP` означает, что карта
работает. Для более краткого обзора есть `-br` (*brief*), а `hostname -I`
показывает только адреса:

```sh
ip -br a
hostname -I
```

Во многих руководствах вам ещё встретится старая команда `ifconfig` (из
пакета *net-tools*), но в современных дистрибутивах она по умолчанию не
установлена. `ip` умеет всё то же самое и даже больше.

## localhost – сам компьютер

У адреса `127.0.0.1` есть имя **localhost**, и он всегда означает «этот
компьютер». Программы на одном компьютере часто общаются друг с другом через
localhost – например, веб-сервер, который вы разрабатываете, и браузер, в
котором вы его проверяете. Трафик на localhost никогда не покидает компьютер.

## Маска сети и шлюз

`/24` после адреса – это **маска сети**. Она говорит, что первые 24 бита
(первые три числа, `192.168.1`) – это адрес сети. Все компьютеры, чей адрес
начинается с `192.168.1.`, находятся в одной локальной сети, и до них можно
достучаться напрямую. Всё остальное отправляется на **шлюз** (*gateway*) –
роутер, – который передаёт это дальше в интернет. Это видно в таблице
маршрутизации:

```sh
ip route
```

```text
default via 192.168.1.1 dev enp0s3 proto dhcp src 192.168.1.42 metric 100
192.168.1.0/24 dev enp0s3 proto kernel scope link src 192.168.1.42 metric 100
```

Первая строка, **default**, – маршрут по умолчанию: «всё, что не указано в
других местах, идёт на 192.168.1.1». Вторая строка говорит, что вся сеть
`192.168.1.0/24` доступна напрямую через `enp0s3`. `proto dhcp` означает, что
компьютер получил настройки автоматически от роутера по **DHCP**.

## ping – доступен ли он?

`ping` отправляет небольшие тестовые пакеты и измеряет, сколько времени
занимают ответы. С помощью `-c` (*count*) вы выбираете количество пакетов –
иначе ping будет работать, пока вы не нажмёте **Ctrl+C**:

```sh
ping -c 3 192.168.1.1
```

```text
64 bytes from 192.168.1.1: icmp_seq=1 ttl=64 time=0.756 ms
...
3 packets transmitted, 3 received, 0% packet loss, time 2004ms
```

- `time=` – время ответа. Внутри домашней сети меньше миллисекунды, до
  интернета часто 10–50 мс.
- `0% packet loss` – ни один пакет не пропал. Потерянные пакеты говорят о
  плохой сети (или плохом соединении по Wi-Fi).
- `Destination Host Unreachable` означает, что ни у одного компьютера в
  локальной сети нет такого адреса.

Попробуйте также пропинговать сам компьютер и компьютер в интернете:

```sh
ping -c 2 localhost
ping -c 3 example.com
```

Внимание! Многие серверы и файрволы намеренно не отвечают на ping. Поэтому
отсутствие ответа не всегда означает, что компьютер выключен.

## Имена и DNS

Люди запоминают имена, компьютеры используют адреса. **DNS** (*Domain Name
System*) – это телефонная книга интернета, которая переводит `example.com` в
IP-адрес. Какой DNS-сервер опрашивает компьютер, записано в
`/etc/resolv.conf`:

```sh
cat /etc/resolv.conf
```

В Ubuntu и Fedora там указан `127.0.0.53` – это **systemd-resolved**,
локальный посредник на вашем собственном компьютере, который в свою очередь
спрашивает роутер. В Debian и Arch роутер, `192.168.1.1`, указан напрямую.

Чтобы самому обратиться к DNS, используют `dig`, `host` или `nslookup`. Они
не установлены изначально, а входят в пакет, который в разных дистрибутивах
называется по-разному:

:::debian
```sh
sudo apt update
sudo apt install dnsutils
```
:::

:::arch
```sh
sudo pacman -S bind
```

Пакет называется `bind` в честь DNS-сервера BIND, из которого происходят эти
инструменты.
:::

:::redhat
```sh
sudo dnf install bind-utils
```
:::

`dig` показывает весь ответ DNS-сервера. Самое важное находится под
`ANSWER SECTION`. С `+short` вы получите только адрес:

```sh
dig example.com
dig +short example.com
```

`host` и `nslookup` делают то же самое с более коротким выводом. `nslookup`
есть также в Windows и macOS. `host` умеет ещё и **обратный поиск** – от
адреса к имени:

```sh
host example.com
nslookup archlinux.org
host 1.1.1.1
```

Можно обратиться к конкретному DNS-серверу с помощью `@`, например к
`1.1.1.1` от Cloudflare или `8.8.8.8` от Google:

```sh
dig @8.8.8.8 +short debian.org
```

## /etc/hosts – собственный список имён компьютера

Прежде чем спрашивать DNS, компьютер заглядывает в файл `/etc/hosts`. Там,
среди прочего, написано, что `localhost` – это `127.0.0.1`:

```sh
cat /etc/hosts
```

У сервера в домашней сети адрес `192.168.1.10`, но имени `server.lan` нет ни
в одном DNS:

```sh
ping -c 1 server.lan
```

Решение – добавить строку в `/etc/hosts`. Файл принадлежит root, поэтому
нужен `sudo`. Но осторожно – вот так **не** получится:

```text
sudo echo '192.168.1.10 server.lan' >> /etc/hosts
bash: /etc/hosts: Permission denied
```

`sudo` действует только на `echo`. Файл для `>>` открывает ваш собственный
shell (который работает от вашего имени, а не от root). Хитрость в том, чтобы
использовать `tee -a`, который дописывает полученное из pipe в конец файла, –
а `tee` можно запустить через sudo:

```sh
echo '192.168.1.10 server.lan' | sudo tee -a /etc/hosts
ping -c 3 server.lan
```

Теперь имя работает для всех программ на компьютере. Но `dig` обращается
напрямую к DNS и игнорирует `/etc/hosts`, поэтому он по-прежнему ничего не
находит. Чтобы увидеть, что разрешает *система*, используйте `getent`:

```sh
dig +short server.lan
getent hosts server.lan
```

Порядок (сначала файл, потом DNS) задаётся строкой `hosts:` в
`/etc/nsswitch.conf`.

## Порты и службы

IP-адрес указывает на компьютер. **Порт** (число от 1 до 65535) указывает на
программу на этом компьютере – как адрес дома и номер квартиры. Про
программу, которая ждёт подключений, говорят, что она **слушает** порт.
Несколько известных портов:

| Порт | Служба |
|---|---|
| 22 | SSH – вход на другие компьютеры |
| 53 | DNS |
| 80 | HTTP – веб |
| 443 | HTTPS – зашифрованный веб |
| 8080 | Часто веб-серверы во время разработки |

Открывать порты ниже 1024 может только root. `ss` (*socket statistics*)
показывает, какие порты слушаются:

```sh
ss -tulpn
```

Флаги обычно запоминают как скороговорку: **t**cp, **u**dp, **l**istening,
**p**rocess, **n**umeric. `0.0.0.0:22` означает, что `sshd` слушает порт 22
на всех адресах компьютера, а `[::]:22` – то же самое для IPv6. Столбец
*Process* пуст для процессов, принадлежащих другим пользователям, – с `sudo`
вы увидите их все:

```sh
sudo ss -tulpn
```

Если учебный сервер `minserver` из главы о процессах запущен, вы увидите его
здесь на порту 8080. Старая команда `netstat -tulpn` (из *net-tools*) делает
то же самое.

## Загрузка из интернета: curl и wget

`curl` загружает то, что находится по адресу (**URL**), и выводит это в
терминал. Попробуйте на minserver на своём компьютере:

:::debian
В Debian и Ubuntu `curl` не предустановлен (а `wget` – да):

```sh
sudo apt install curl
```
:::

```sh
curl http://localhost:8080
```

Получили `Couldn't connect to server`? Значит, порт никто не слушает –
возможно, вы остановили minserver в главе о процессах. Запустите его снова:

```sh
minserver
```

С `-I` curl показывает только **заголовки** ответа, где первая строка – это
**код состояния**:

```sh
curl -I https://example.com
```

| Код | Означает |
|---|---|
| 200 | OK |
| 301, 302 | Страница переехала – смотрите `Location:` |
| 403 | Доступ запрещён |
| 404 | Не найдено |
| 500 | Ошибка сервера |

Многие сайты перенаправляют с `http://` на `https://`. Тогда вы получите
лишь короткое «301 Moved Permanently». С `-L` curl последует за
перенаправлением:

```sh
curl -I http://linux.org
curl -L http://linux.org
```

Поскольку curl пишет в терминал, он отлично работает в pipe. `-s` (*silent*)
отключает индикатор прогресса:

```sh
curl -s https://example.com | grep title
```

Чтобы сохранить в файл, используйте `-o ФАЙЛ` (или `-O`, который берёт имя
файла из адреса):

```sh
cd ~
curl -o exempel.html https://example.com
```

`wget` создан для скачивания файлов. Он всегда сохраняет в файл, показывает
прогресс и сам следует за перенаправлениями:

:::arch
В Arch `wget` не предустановлен (а `curl` – да):

```sh
sudo pacman -S wget
```
:::

:::redhat
В Fedora `wget` не предустановлен (а `curl` – да):

```sh
sudo dnf install wget
```
:::

```sh
wget https://example.com/cheatsheet.txt
cat cheatsheet.txt
```

Чтобы самому выбрать имя файла, используйте заглавную `-O`:
`wget -O file.html URL`.

## SSH – вход на другой компьютер

**SSH** (*Secure Shell*) – обычный способ удалённо управлять компьютером с
Linux, и всё передаваемое шифруется. На сервере работает служба `sshd` на
порту 22, а подключаетесь вы с помощью клиента `ssh`:

:::arch
В Arch клиент ssh не предустановлен:

```sh
sudo pacman -S openssh
```
:::

```sh
ssh elev@server.lan hostname
```

`elev@server.lan` означает «пользователь elev на компьютере server.lan».
Команда после хоста (`hostname`) выполняется на сервере, а ответ
показывается здесь – там написано `server`, а не {{hostname}}.

При первом подключении к компьютеру ssh спрашивает, доверяете ли вы ему:

```text
The authenticity of host 'server.lan (192.168.1.10)' can't be established.
ED25519 key fingerprint is SHA256:q7Jx3MmP0yZk8VbW1sTn4dLr9HcE2uFgA6oYiKjN5Rw.
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

Введите `yes` (всё слово целиком). После этого **ключ хоста** сервера
сохраняется в `~/.ssh/known_hosts`. Если ключ позже изменится, ssh громко
предупредит – это может означать, что кто-то выдаёт себя за сервер.

Команда может состоять из нескольких команд в кавычках:

```sh
ssh elev@server.lan 'whoami; uptime; ls'
ssh elev@server.lan cat välkommen.txt
```

Без команды ssh входит в систему, и вы получаете shell на другом компьютере,
из которого выходят с помощью `exit`. В симуляторе это не поддерживается –
там вы всегда пишете команду сразу после хоста.

### Ключи вместо паролей

Вместо пароля можно входить с помощью **пары ключей**. Закрытый ключ остаётся
у вас, а открытый помещается на сервер:

```sh
ssh-keygen
ssh-copy-id elev@server.lan
```

Нажимайте Enter на вопросы `ssh-keygen`, чтобы использовать файл по
умолчанию `~/.ssh/id_ed25519` без парольной фразы. `ssh-copy-id` добавляет
открытый ключ (`id_ed25519.pub`) в `~/.ssh/authorized_keys` на сервере. После
этого ssh больше не спрашивает пароль. Никогда никому не показывайте
закрытый ключ!

С помощью `scp` и `rsync` можно копировать файлы по SSH, а в файле
`~/.ssh/config` можно дать серверам короткие имена – но это подождёт до
одной из следующих глав.

## Когда сеть не работает

«Интернет не работает» может иметь много причин. Пройдите шаги по порядку,
изнутри наружу – первый шаг, который не удался, показывает, где проблема:

| Шаг | Команда | Если не получается |
|---|---|---|
| 1. Есть ли у меня адрес? | `ip a` | Карта выключена (`state DOWN`) или не получила адрес |
| 2. Есть ли путь наружу? | `ip route` | Нет строки `default` – нет шлюза |
| 3. Доступен ли роутер? | `ping -c 3 192.168.1.1` | Проблема в локальной сети (кабель, Wi-Fi) |
| 4. Доступен ли интернет? | `ping -c 3 1.1.1.1` | Проблема на роутере или у провайдера |
| 5. Работает ли DNS? | `ping -c 3 example.com` | Поиск имён не работает – проверьте `/etc/resolv.conf` |

На шаге 4 пингуется адрес напрямую, без всякого имени. Если шаг 4 работает,
а шаг 5 – нет, то почти всегда сломан DNS – это одна из самых частых
проблем.

Попробуйте сами! Выключите сетевую карту, пройдите шаги и затем снова
включите её:

```sh
sudo ip link set enp0s3 down
ip a
ip route
ping -c 3 192.168.1.1
ping -c 3 example.com
sudo ip link set enp0s3 up
```

## Пакеты

Сетевые инструменты находятся в разных пакетах – и, как обычно, в разных
семействах они называются по-разному:

| Инструмент | Debian/Ubuntu | Arch | Fedora |
|---|---|---|---|
| `ip`, `ss` | `iproute2` | `iproute2` | `iproute` |
| `ping` | `iputils-ping` | `iputils` | `iputils` |
| `dig`, `host`, `nslookup` | `dnsutils` | `bind` | `bind-utils` |
| `traceroute` | `traceroute` | `traceroute` | `traceroute` |
| `ssh`, `ssh-keygen` | `openssh-client` | `openssh` | `openssh-clients` |

`traceroute` показывает каждый роутер, через который проходят пакеты по
пути. Установите его и попробуйте `traceroute example.com`!

|---|---|

| `ping -c 3 ХОСТ` | Проверяет, доступен ли компьютер |
| `dig +short ИМЯ` | Ищет имя в DNS |
