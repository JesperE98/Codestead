# Git в терминале

Вам случалось сохранять файлы с именами `report-final.txt`, `report-final-2.txt`
и `report-REALLY-final.txt`? Значит, вы уже занимались *контролем версий*
вручную. Система контроля версий делает то же самое, но как следует: она
сохраняет снимки всего проекта, помнит, кто что изменил и зачем, позволяет
путешествовать назад во времени и даёт многим людям работать над одними и
теми же файлами одновременно.

**Git** – самая распространённая система контроля версий, причём с большим
отрывом. Её написал в 2005 году Линус Торвальдс – тот самый человек, который
написал ядро Linux, – чтобы управлять исходным кодом ядра. Сегодня git
используется почти для любого программного обеспечения, но он так же хорошо
подходит для веб-страниц, конфигурационных файлов, заметок и книг. Всё, что
является текстом, подходит идеально.

Git создан для терминала. В графических программах и редакторах есть кнопки
для git, но под капотом они выполняют те же команды, которые вы изучите здесь.

## Установка git

Git не всегда установлен заранее. В терминале Ubuntu он устанавливается с
помощью apt:

```sh
sudo apt update
sudo apt install git
```

В других дистрибутивах его устанавливают их собственным пакетным менеджером,
как вы узнали в части о дистрибутивах и пакетах, – пакет и там называется
`git`. Проверьте, что он работает:

```sh
git --version
```

Все команды git имеют вид `git КОМАНДА`, например `git status` или `git log`.
Руководство открывается командой `man git`.

## Представьтесь git

Каждая сохранённая версия в git содержит имя и адрес электронной почты того,
кто её сделал. Поэтому git хочет знать, кто вы, прежде чем вы сможете что-либо
сохранить. Это настраивается один раз на каждом компьютере:

```sh
git config --global user.name "{{gitName}}"
git config --global user.email "{{user}}@example.com"
```

Можете указать своё имя. `--global` означает, что настройка действует для
всех ваших проектов. Она хранится в обычном текстовом файле `~/.gitconfig`:

```sh
cat ~/.gitconfig
```

```text
[user]
	name = {{gitName}}
	email = {{user}}@example.com
```

Если пропустить этот шаг, git возмутится, когда вы попытаетесь что-то
сохранить: `*** Please tell me who you are.` – и предложит выполнить ровно эти
две команды.

> **Совет:** Добавьте также `git config --global init.defaultBranch main`.
> Тогда основная ветка каждого нового проекта на всех ваших компьютерах будет
> называться `main`. В старых версиях git она называется `master`, и в мире
> вам встретятся оба названия.

## Новый репозиторий

В вашем домашнем каталоге есть небольшой веб-проект `~/{{webProject}}`
с тремя файлами. Перейдите туда и осмотритесь:

```sh
cd ~/{{webProject}}
ls
```

Чтобы git начал следить за каталогом, превратите его в **репозиторий**
(сокращённо – *репо*):

```sh
git init
```

```text
Initialized empty Git repository in /home/{{user}}/{{webProject}}/.git/
```

Произошло только одно: был создан скрытый каталог `.git`. Именно там git
хранит всю историю. Ваши файлы git не трогает.

```sh
ls -a
ls .git
```

Никогда не удаляйте `.git`, если не хотите потерять историю, – и не
редактируйте файлы в нём вручную. Если вы хотите перестать использовать git в
проекте, достаточно удалить `.git`; ваши обычные файлы останутся.

```quiz
Вы хотите перестать использовать git в проекте, но сохранить все файлы. Что нужно сделать?
- [ ] Ещё раз выполнить `git init`
- [x] Удалить скрытый каталог `.git`
- [ ] Удалить все файлы, кроме `.git`
---
Вся история хранится в `.git`, а ваши обычные файлы git не трогает. Без `.git`
файлы остаются – пропадает только история.
```

## Три места: рабочий каталог, индекс и история

Самое важное, что нужно понять о git, – это то, что изменение проходит через
три места:

```text
 рабочий каталог  ──git add──▶  индекс  ──git commit──▶  история
 (файлы, которые вы видите)    (следующий коммит)       (.git)
```

- **Рабочий каталог** (*working tree*) – это файлы в том виде, в каком они
  есть прямо сейчас, те, которые вы редактируете.
- **Индекс** (его также называют *staging area*) – это что-то вроде
  упаковочного стола. Туда вы кладёте то, что должно войти в следующую
  сохранённую версию.
- **История** состоит из **коммитов**. Коммит – это сохранённый снимок всех
  файлов с сообщением, автором и временем.

Зачем нужен промежуточный шаг? Чтобы вы могли выбирать. Если вы изменили пять
файлов, но вместе связаны только два, вы можете положить эти два в индекс,
закоммитить их, а остальное оставить для отдельного коммита.

```quiz
Вы изменили пять файлов, но вместе связаны только два изменения. Как сохранить
в коммите только эти два?
- [ ] Сначала выполнить `git commit`, а потом `git add` для двух файлов
- [x] Выполнить `git add` для двух файлов, затем `git commit`
- [ ] Закоммитить все пять – коммит всегда берёт все изменённые файлы
---
Коммит сохраняет то, что находится в индексе. Остальные три изменения остаются
в рабочем каталоге, пока вы их не добавите.
```

## `git status` – ваш компас

Чаще всего вы будете выполнять команду `git status`. Она показывает, где
находится каждое изменение, – и часто подсказывает, что делать дальше. Лучше
запускать её слишком часто, чем слишком редко!

```sh
git status
```

```text
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	README.md
	index.html
	style.css

nothing added to commit but untracked files present (use "git add" to track)
```

*Untracked files* – это файлы, которые git видит, но пока не отслеживает. В
настоящем терминале они показываются красным. Положите их в индекс командой
`git add`:

```sh
git add index.html style.css README.md
git status
```

```text
Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   README.md
	new file:   index.html
	new file:   style.css
```

Теперь они перечислены в разделе *Changes to be committed* – зелёным. Вместо
того чтобы называть каждый файл, можно написать `git add .` – это добавит всё
в текущем каталоге (точка означает «здесь»). `git add -A` добавляет все
изменения во всём репозитории.

## Первый коммит

Сохраните снимок командой `git commit`. Опция `-m` задаёт сообщение:

```sh
git commit -m "{{commitFirst}}"
```

```text
[main (root-commit) 3f2a9c1] {{commitFirst}}
 3 files changed, 24 insertions(+)
 create mode 100644 README.md
 create mode 100644 index.html
 create mode 100644 style.css
```

`3f2a9c1` – начало **идентификатора** коммита: 40-символьного
*хеша*, вычисленного из содержимого. Ваш идентификатор будет другим, ведь в
него входят время и ваше имя. Обычно первых семи символов достаточно, чтобы
однозначно указать коммит.

Снова выполните `git status`:

```sh
git status
```

```text
On branch main
nothing to commit, working tree clean
```

*Working tree clean* означает, что всё сохранено. Отлично!

## Что изменилось: `git diff`

Добавьте строку в `README.md` и спросите git, что произошло:

```sh
echo '{{builtWith}}' >> README.md
git status
git diff
```

```text
diff --git a/README.md b/README.md
index 1100cf4..e5bd3a0 100644
--- a/README.md
+++ b/README.md
@@ -1,3 +1,4 @@
 # {{siteTitle}}
 
 Небольшой сайт, версии которого я храню в git.
+{{builtWith}}
```

Строка, начинающаяся с `+`, новая (зелёная), строки, начинающиеся с `-`, были
удалены (красные), а остальные показаны для контекста. `@@ -1,3 +1,4 @@`
означает, что строкам 1–3 старой версии соответствуют строки 1–4 новой.

`git diff` сравнивает рабочий каталог с индексом – то есть показывает то, что
вы *ещё не* добавили. Чтобы увидеть, что лежит в индексе и ждёт коммита,
наберите `git diff --staged`.

Добавьте и закоммитьте изменение. Опция `-a` выполняет `git add` для всех
файлов, которые git уже отслеживает, так что хватит одного шага:

```sh
git commit -a -m "{{commitDescribe}}"
```

Обратите внимание: `-a` *не* включает новые файлы, которые git пока не
отслеживает. Их всегда нужно сначала добавить через `git add`.

Вопросы с командами в этой главе начинаются в новом терминале, поэтому
сначала они устанавливают git и делают первый коммит. `> /dev/null 2>&1`
выбрасывает вывод этих строк, как вы узнали в главе о перенаправлении и
конвейерах. Что выведет последняя команда?

```predict
$ sudo apt update > /dev/null 2>&1 && sudo apt install -y git > /dev/null 2>&1
$ git config --global user.name "{{gitName}}"
$ git config --global user.email "{{user}}@example.com"
$ cd ~/{{webProject}} && git init > /dev/null 2>&1
$ git add . && git commit -m "Первая версия" > /dev/null
$ echo 'Ещё одна строка.' >> README.md
$ git commit -m "Ещё одна строка" > /dev/null
$ git log --oneline | wc -l
1
---
Второго коммита так и не случилось: изменения в `README.md` не было в индексе,
поэтому коммитить было нечего. Сначала `git add README.md` – или
`git commit -a` – и коммитов было бы два.
```

## Хорошие сообщения коммитов

Через полгода именно сообщения коммитов будут рассказывать историю – вам и
другим. Несколько практических правил:

- Пишите короткую первую строку, лучше не длиннее 50 символов, которая
  описывает суть изменения.
- Описывайте, *что* делает изменение и желательно *зачем*, а не *как* вы его
  писали.
- Один коммит – одно дело. Три маленьких коммита лучше одного большого.
- Нужно объяснить подробнее? Оставьте пустую строку и напишите ниже более
  длинный текст. Каждая `-m` становится отдельным абзацем:
  `git commit -m "Заголовок" -m "Пояснение."`

| Плохо | Лучше |
|---|---|
| `fix` | `Исправить битую ссылку на страницу контактов` |
| `изменения` | `Увеличить заголовки на мобильных` |
| `asdf` | `Добавить форму обратной связи` |

По-английски сообщения обычно пишут в повелительном наклонении: *Add contact
form*, *Fix broken link*. Это читается как «этот коммит …». По-русски часто
пишут так же – инфинитивом («Добавить форму») – или в прошедшем времени
(«Добавил форму»); главное – придерживаться одного стиля.

## Просмотр истории

```sh
git log
```

```text
commit 8d41b7e0c2a3f1d5e9b6a7c8d9e0f1a2b3c4d5e6 (HEAD -> main)
Author: {{gitName}} <{{user}}@example.com>
Date:   Fri Oct 30 14:12:09 2026 +0100

    {{commitDescribe}}

commit 3f2a9c1...
```

Самый новый коммит идёт первым. `HEAD -> main` означает, что вы находитесь на
ветке `main` и что это её последний коммит. Несколько полезных вариантов:

```sh
git log --oneline
git log -n 1
git log --stat
git show
```

`--oneline` выводит по одной строке на коммит, `-n 1` показывает только
последний, `--stat` – какие файлы изменились, а `git show` показывает коммит
вместе с самим изменением. Можно также посмотреть, как выглядел файл в
определённом коммите: `git show HEAD~1:README.md` (`HEAD~1` означает «коммит
перед последним»).

## Отмена изменений

Git позволяет легко отменять изменения – в этом половина его смысла:

| Если вы хотите … | Команда |
|---|---|
| выбросить изменения в файле (ещё не добавленные) | `git restore ФАЙЛ` |
| убрать файл из индекса (изменение останется) | `git restore --staged ФАЙЛ` |
| изменить сообщение последнего коммита | `git commit --amend -m "Новое сообщение"` |
| вернуть всё к состоянию последнего коммита | `git reset --hard` |

Попробуйте испортить файл и вернуть его обратно:

```sh
echo 'oops' > index.html
git diff
git restore index.html
cat index.html
```

> **Внимание!** `git restore ФАЙЛ` и `git reset --hard` выбрасывают
> изменения, которые так и не были закоммичены. Их нельзя восстановить. А вот
> то, что когда-либо было закоммичено, почти всегда можно спасти – спросите
> у `git reflog`, где вы побывали.

## Ветки

**Ветка** – это отдельная линия разработки. В ветке можно опробовать новую
идею, не трогая рабочую версию в `main`. Если всё получилось, вы сливаете
ветку с `main`; если нет – просто выбрасываете её.

Технически ветка – это всего лишь метка, которая указывает на коммит и
сдвигается вперёд, когда вы делаете новые коммиты. Поэтому ветки в git
дешёвые – пользуйтесь ими часто!

```sh
git branch
git switch -c {{newDesign}}
git branch
```

`git switch -c {{newDesign}}` создаёт ветку и
переключается на неё. Звёздочка в выводе `git branch` показывает, где вы
находитесь. Внесите изменение и закоммитьте его в ветке:

```sh
echo 'h1 { color: purple; }' >> style.css
git commit -am "{{commitPurple}}"
```

Вернитесь на `main` и посмотрите на `style.css`:

```sh
git switch main
tail -3 style.css
```

Фиолетовый цвет исчез! При переключении веток git переписывает рабочий
каталог так, чтобы он соответствовал последнему коммиту ветки. Изменение надёжно
сохранено в `{{newDesign}}`. `git log --oneline --all` показывает все ветки:

```sh
git log --oneline --all
```

> **Совет:** В старых руководствах часто используют `git checkout {{newDesign}}` и
> `git checkout -b new-branch`. `checkout` делает то же, что `switch`, но
> умеет ещё и восстанавливать файлы. Более новые команды `switch` и `restore`
> разделяют эти задачи, и их проще запомнить.

Незакоммиченные изменения переносятся вместе с вами при переключении веток –
если только они не конфликтуют с другой веткой. Тогда git откажется и
попросит сначала сделать коммит (или временно отложить изменения командой
`git stash` и вернуть их потом командой `git stash pop`).

В исходном `style.css` нет ни одного `purple` – заголовки в нём тёмно-синие
(`navy`). Сколько строк со словом `purple` будет в `style.css` в конце?

```predict
$ sudo apt update > /dev/null 2>&1 && sudo apt install -y git > /dev/null 2>&1
$ git config --global user.name "{{gitName}}"
$ git config --global user.email "{{user}}@example.com"
$ cd ~/{{webProject}} && git init > /dev/null 2>&1
$ git add . && git commit -m "Первая версия" > /dev/null
$ git switch -c {{newDesign}} > /dev/null 2>&1
$ echo 'h1 { color: purple; }' >> style.css
$ git commit -am "{{commitPurple}}" > /dev/null
$ git switch main > /dev/null 2>&1
$ grep purple style.css | wc -l
0
---
Строка с purple была закоммичена в `{{newDesign}}`. Когда вы переключаетесь на
`main`, git приводит рабочий каталог к последнему коммиту `main` – а там этой
строки ещё нет.
```

## Слияние веток: `git merge`

Встаньте на ветку, которая должна *получить* изменения, – здесь это `main` –
и выполните слияние:

```sh
git merge {{newDesign}}
```

```text
Updating 8d41b7e..c19e2f4
Fast-forward
 style.css | 1 +
 1 file changed, 1 insertion(+)
```

*Fast-forward* («перемотка вперёд») означает, что `main` не менялась с тех
пор, как была создана ветка. Тогда git остаётся только передвинуть `main`
вперёд на тот же коммит, что и `{{newDesign}}`.

Если в обеих ветках есть новые коммиты, git выполняет **трёхстороннее
слияние**: он сравнивает обе ветки с их общим предком и создаёт новый *коммит
слияния* (*merge commit*) с двумя родителями. `git log --oneline --graph --all`
показывает, как история расходится и снова сходится:

```text
*   e4b1d0a (HEAD -> main) Merge branch 'heading'
|\
| * 7c3f9e2 (heading) Более дружелюбный заголовок
* | 52d8a71 Более короткий текст
|/
* c19e2f4 {{commitPurple}}
```

Слитая ветка больше не нужна, и её можно удалить. `-d` откажется это делать,
если в ветке есть коммиты, которых нет в той, на которой вы находитесь:

```sh
git branch -d {{newDesign}}
```

## Конфликты

Если в обеих ветках изменены *одни и те же строки*, git не может знать, какая
версия правильная. Это называется **конфликтом**, и тогда решаете вы. Давайте
создадим конфликт нарочно:

```sh
git switch -c heading
sed -i 's/Добро пожаловать!/Привет и добро пожаловать!/' index.html
git commit -am "Более дружелюбный заголовок"
git switch main
sed -i 's/Добро пожаловать!/Добро пожаловать на мой сайт!/' index.html
git commit -am "Более длинный заголовок"
git merge heading
```

```text
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.
```

Спокойно – ничего не сломалось. `git status` показывает файл в разделе
*Unmerged paths* как `both modified`. Загляните в него:

```sh
git status
cat index.html
```

```text
<<<<<<< HEAD
  <h1>Добро пожаловать на мой сайт!</h1>
=======
  <h1>Привет и добро пожаловать!</h1>
>>>>>>> heading
```

Между `<<<<<<< HEAD` и `=======` находится ваша версия (ветки, на которой вы
стоите); между `=======` и `>>>>>>> heading` – версия другой ветки. Конфликт
разрешается так:

1. Откройте файл в редакторе и приведите его к нужному виду – выберите одну из
   строк или объедините их – и удалите строки-маркеры.
2. Сообщите git, что конфликт разрешён, командой `git add ФАЙЛ`.
3. Завершите слияние командой `git commit`.

Настоящего редактора в симуляторе нет, но если вы просто хотите выбрать
версию одной из сторон, git сделает это за вас: `--ours` берёт вашу версию, а
`--theirs` – версию другой ветки.

```sh
git checkout --theirs index.html
git add index.html
git status
git commit -m "Слить ветку heading"
```

Если вы передумаете посреди конфликта, `git merge --abort` вернёт вас туда,
где вы были до слияния.

Конфликты – совершенно нормальное дело, когда над одним проектом работают
несколько человек. Хороший способ сделать их реже – делать маленькие коммиты
и часто сливать ветки.

```quiz
Вы находитесь в `main` и выполняете `git merge heading`. В файле возникает конфликт:

    <<<<<<< HEAD
      <h1>Hello!</h1>
    =======
      <h1>Welcome!</h1>
    >>>>>>> heading

Какая строка пришла из `main`?
- [x] `<h1>Hello!</h1>`
- [ ] `<h1>Welcome!</h1>`
---
`HEAD` – это ветка, на которой вы находитесь, здесь `main`. Её версия стоит
между `<<<<<<< HEAD` и `=======`; версия другой ветки идёт после `=======`.
```

## Файлы, которые git должен игнорировать: `.gitignore`

Некоторые файлы никогда не должны попадать в историю: пароли и ключи, логи,
временные файлы и всё, что собирается автоматически. Запишите их имена или
шаблоны в файл `.gitignore` в корне репозитория:

```sh
echo 'password=secret' > secret.txt
echo 'error' > error.log
printf 'secret.txt\n*.log\nbuild/\n' > .gitignore
git status
```

```text
Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore
```

`secret.txt` и `error.log` больше не показываются –
их не подхватывает даже `git add .`. `*` соответствует чему угодно, а косая
черта в конце (`build/`) означает целый каталог. А вот сам `.gitignore` нужно
закоммитить, чтобы все, кто работает над проектом, игнорировали одно и то же:

```sh
git add .gitignore
git commit -m "Игнорировать секреты и логи"
```

Учтите, что `.gitignore` действует только на файлы, которые git ещё не
отслеживает. Если файл уже закоммичен, удалите его из репозитория (но не с
диска) командой `git rm --cached ФАЙЛ`.

## GitHub, GitLab и удалённые репозитории

До сих пор всё жило в вашем собственном репозитории. Чтобы работать вместе с
другими или просто иметь резервную копию, обычно хранят копию репозитория на
сервере – **удалённый репозиторий** (*remote*). Самые известные сервисы –
**GitHub**, **GitLab** и **Codeberg**.

| Команда | Что делает |
|---|---|
| `git clone URL` | Скачивает весь репозиторий со всей историей в новый каталог |
| `git push` | Отправляет ваши новые коммиты в удалённый репозиторий |
| `git pull` | Получает новые коммиты из удалённого репозитория и сливает их с вашими |
| `git fetch` | Получает новые коммиты, ничего не сливая |
| `git remote -v` | Показывает список удалённых репозиториев |

Удалённый репозиторий обычно называется `origin`, а типичный рабочий процесс
выглядит так: `git pull`, когда вы начинаете, затем правки, `git add` и
`git commit` – и в конце `git push`. Для входа GitHub и GitLab используют
SSH-ключ или токен доступа, а не пароль.

Для всего этого нужна сеть, а в симуляторе её нет. Но `clone`, `push` и
`pull` так же хорошо работают между двумя репозиториями на одном компьютере,
так что попробовать всё равно можно. Склонируйте свой проект в новый каталог:

```sh
cd ~
git clone ~/{{webProject}} ~/copy
cd ~/copy
git log --oneline
git remote -v
```

На сервере вроде GitHub есть только история, без рабочего каталога. Такой
*голый* (*bare*) репозиторий создаётся командой `git init --bare`.
Представьте, что это ваш аккаунт на GitHub, и отправьте туда `main`:

```sh
git init --bare ~/server.git
cd ~/{{webProject}}
git remote add origin ~/server.git
git push -u origin main
git status
```

`-u` связывает вашу `main` с `origin/main`, чтобы `git status` мог сообщать,
опережаете вы сервер или отстаёте от него, и чтобы дальше хватало просто
`git push` и `git pull`.

## Итоги

| Команда | Что делает |
|---|---|
| `git init` | Превращает каталог в репозиторий |
| `git status` | Показывает состояние – запускайте часто! |
| `git add ФАЙЛ` / `git add .` | Кладёт изменения в индекс |
| `git commit -m "…"` | Сохраняет индекс как новый коммит |
| `git diff` / `git diff --staged` | Показывает незакоммиченные изменения |
| `git log --oneline --graph --all` | Показывает историю |
| `git restore ФАЙЛ` | Выбрасывает изменения в файле |
| `git switch -c ВЕТКА` | Создаёт ветку и переключается на неё |
| `git merge ВЕТКА` | Сливает ветку с той, на которой вы находитесь |
| `git clone`, `git pull`, `git push` | Совместная работа через удалённый репозиторий |
