# Службы и журналы с systemd

Компьютер с Linux постоянно делает то, что никто не запускает вручную: он
принимает SSH-подключения, синхронизирует часы, выполняет задания по
расписанию и пишет журналы. Программы, которые этим занимаются, называются
**службами** (*services*), и почти в каждом современном дистрибутиве за
порядком среди них следит **systemd**. В этой главе вы научитесь запускать и
останавливать службы, настраивать их автозапуск при загрузке и – самое
важное – читать журналы, когда что-то идёт не так.

## init и systemd

Когда ядро Linux загрузилось, оно запускает одну-единственную программу:
**init**, процесс номер 1. Затем init запускает всё остальное. Сегодня init
почти всегда – это **systemd**: и в Debian, и в Ubuntu, и в Arch, и в Fedora.
Посмотрите сами:

```sh
ps -p 1
```

Процесс называется `/sbin/init`, но это всего лишь ссылка на программу
`systemd`.

systemd умеет больше, чем просто запускать службы. Он следит, живы ли они,
перезапускает их при падении (если вы этого хотите), собирает всё, что они
выводят, в общий журнал – **journal** – и имеет инструменты для большинства
частей системы:

| Инструмент | Что делает |
|---|---|
| `systemctl` | Управляет службами: состояние, запуск, остановка, загрузка |
| `journalctl` | Читает journal (журнал) |
| `hostnamectl` | Показывает и меняет имя компьютера |
| `systemd-analyze` | Показывает, сколько длилась загрузка |

## Юниты и службы

Всё, за чем следит systemd, называется **юнитом** (*unit*). Бывают юниты
разных видов, и вид виден по суффиксу: `.service` (служба), `.timer`
(задание по расписанию), `.socket`, `.mount`, `.target` (группа юнитов,
что-то вроде «уровня» загрузки) и другие. Эта глава посвящена службам.

Каждый юнит описывается **юнит-файлом** – небольшим текстовым файлом. Они
лежат в двух местах:

| Каталог | Содержимое |
|---|---|
| `/usr/lib/systemd/system/` | Юнит-файлы, поставляемые с пакетами. Здесь ничего не редактируйте! |
| `/etc/systemd/system/` | Собственные юнит-файлы администратора. Они имеют приоритет. |

```sh
ls /usr/lib/systemd/system
ls /etc/systemd/system
```

В старых версиях Debian и Ubuntu вместо этого часто указано
`/lib/systemd/system`. Это тот же самый каталог – `/lib` является ссылкой на
`/usr/lib`.

Имя службы – это имя файла, например `minserver.service`. При вводе команд
`.service` можно опускать: `systemctl status minserver` работает точно так
же.

## Как дела у службы? – `systemctl status`

Чаще всего вы будете пользоваться командой `systemctl status`:

```sh
systemctl status ssh
```

В Ubuntu SSH-сервер называется `ssh`. Вывод выглядит примерно так:

```text
● ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/usr/lib/systemd/system/ssh.service; enabled; preset: enabled)
     Active: active (running) since Fri 2026-10-30 07:54:07 UTC; 2h 13min ago
       Docs: man:sshd(8)
             man:sshd_config(5)
   Main PID: 733 (sshd)
      Tasks: 1 (limit: 9387)
     Memory: 10.1M
     CGroup: /system.slice/ssh.service
             └─733 /usr/sbin/sshd -D

Oct 30 07:54:07 ubuntu systemd[1]: Starting ssh.service - OpenBSD Secure Shell server...
Oct 30 07:54:07 ubuntu sshd[733]: Server listening on 0.0.0.0 port 22.
Oct 30 07:54:07 ubuntu systemd[1]: Started ssh.service - OpenBSD Secure Shell server.
```

Строка за строкой:

| Строка | Означает |
|---|---|
| `●` | Зелёная точка = работает. Красный `×` = сбой. Белый `○` = остановлена. |
| `Loaded` | Где находится юнит-файл, запускается ли служба при загрузке (`enabled`/`disabled`/`static`) и настройка дистрибутива по умолчанию (`preset`) |
| `Active` | Самая важная строка: `active (running)`, `inactive (dead)` или `failed` – и с какого времени |
| `Docs` | Где почитать подробнее (`man sshd`) |
| `Main PID` | Главный процесс службы – тот же PID, что и в `ps aux` |
| `Memory`, `CGroup` | Сколько памяти она использует и какие процессы к ней относятся |
| Последние строки | Самые свежие строки из журнала службы в journal |

`static` означает, что службу нельзя включить саму по себе – она запускается,
когда она нужна другому юниту.

> **Совет:** В настоящем терминале длинный вывод показывается в пейджере
> (`less`). Нажмите `q`, чтобы вернуться. Добавьте `--no-pager`, если хотите
> обойтись без него.

## Запуск, остановка и перезапуск

```text
sudo systemctl start minserver      # запустить сейчас
sudo systemctl stop minserver       # остановить сейчас
sudo systemctl restart minserver    # остановить и запустить снова
sudo systemctl reload minserver     # попросить перечитать конфигурацию
```

Всё, что что-то **меняет**, требует прав root, так что не забывайте `sudo`.
Без него systemctl ответит:

```text
Failed to start minserver.service: Interactive authentication required.
```

`reload` работает только для служб, которые его поддерживают. Преимущество в
том, что служба при этом продолжает работать – ни одно соединение не
обрывается. Когда вы изменили конфигурационный файл службы, `reload` или
`restart` – последний шаг.

> **Попробуйте!** В главе о процессах вы остановили учебный сервер с помощью
> `pkill`. Посмотрите на `systemctl status minserver` – systemd заметил, что
> процесс исчез. Запустите его снова через `systemctl` и сравните PID с
> `pgrep -l minserver`.

## Сейчас или при загрузке? `start` и `enable`

Это самое распространённое недоразумение насчёт systemd: **`start` и
`enable` – две разные вещи.**

| Команда | Что делает |
|---|---|
| `systemctl start X` | Запускает службу **сейчас**. После перезагрузки её снова нет. |
| `systemctl enable X` | Запускает службу автоматически **при загрузке** – но не сейчас. |
| `systemctl enable --now X` | И то и другое сразу. |
| `systemctl disable X` | Не запускать при загрузке (`--now` заодно останавливает её). |

`enable` создаёт ссылку в каталоге, названном по target из раздела
`[Install]` юнит-файла, обычно `multi-user.target.wants`:

```text
$ sudo systemctl enable --now minserver
Created symlink /etc/systemd/system/multi-user.target.wants/minserver.service → /etc/systemd/system/minserver.service.
```

Когда компьютер загружается, systemd проходит по этому каталогу и запускает
всё, что в нём лежит. Состояние можно запросить:

```sh
systemctl is-active minserver
systemctl is-enabled minserver
```

`is-active` и `is-enabled` отлично подходят для скриптов – они выводят одно
слово и завершаются с кодом 0, если ответ «да». С `-q` они полностью
молчат:

```text
if systemctl is-active -q minserver; then echo "сервер работает"; fi
```

На только что запущенном компьютере в симуляторе `minserver` работает, но
никто его не включил. Что выведут эти две команды?

```predict
$ systemctl is-active minserver
$ systemctl is-enabled minserver
active
disabled
---
minserver работает **сейчас**, но `enable` никто не выполнял – после
перезагрузки он бы не запустился. `start` и `enable` – действительно две
разные вещи.
```

## Список служб

```sh
systemctl list-units --type=service
systemctl list-units --type=service --all
systemctl --failed
systemctl list-unit-files
```

- `list-units` показывает службы, которые работают (или завершились сбоем).
  С `--all` в список попадают и остановленные.
- `--failed` показывает только те, что завершились сбоем. Хорошая первая
  команда, когда кажется, что что-то не так!
- `list-unit-files` показывает все установленные юнит-файлы и то, в каком
  они состоянии: `enabled`, `disabled` или `static`.

## Журнал – `journalctl`

Всё, что выводят службы, ядро и сам systemd, попадает в journal. Без опций
вы получите весь журнал, начиная с самых старых записей:

```sh
journalctl
```

Это быстро становится слишком много, поэтому почти всегда используют
фильтры:

| Команда | Показывает |
|---|---|
| `journalctl -u ssh` | Только одну службу (`-u` как в *unit*) |
| `journalctl -n 20` | 20 последних строк |
| `journalctl -f` | Последние строки, а затем новые по мере появления (выход – Ctrl+C) |
| `journalctl -b` | Только текущую загрузку (`-b -1` = предыдущую) |
| `journalctl --since today` | С полуночи. Также `yesterday`, `"10:00"`, `"1 hour ago"` |
| `journalctl -p err` | Только ошибки и хуже |
| `journalctl -xe` | Перейти в конец и добавить пояснения |
| `journalctl -k` | Только сообщения ядра (как `dmesg`) |

Опции можно комбинировать. Пара классических примеров:

```sh
journalctl -u minserver -n 5
journalctl -p err -b
journalctl --since today -u minserver
```

### Приоритеты

У каждой строки в journal есть **приоритет**. `-p` показывает выбранный
приоритет *и всё, что серьёзнее*:

| Число | Имя | Означает |
|---|---|---|
| 0 | `emerg` | Система непригодна к работе |
| 1 | `alert` | Нужно исправить немедленно |
| 2 | `crit` | Критическая ошибка |
| 3 | `err` | Ошибка – показывается красным |
| 4 | `warning` | Предупреждение – показывается жёлтым |
| 5 | `notice` | Нормально, но стоит обратить внимание |
| 6 | `info` | Информация |
| 7 | `debug` | Отладочная информация |

Не волнуйтесь, если `journalctl -p err` покажет пару ошибок ядра вроде
`ACPI BIOS Error`. Они есть почти на каждом компьютере и обычно безвредны –
это ошибки в прошивке компьютера, которые ядро обходит.

Обычно, чтобы видеть всё, нужно быть root или состоять в группе, которой
разрешено читать журнал (`adm` или `systemd-journal` в Ubuntu – в других
семействах используются другие группы). Вашему пользователю в симуляторе
разрешено читать весь журнал.

```quiz
Какие приоритеты показывает `journalctl -p warning`?
- [x] `err`
- [x] `warning`
- [x] `crit`
- [ ] `notice`
- [ ] `info`
---
`-p` показывает выбранный приоритет *и всё, что серьёзнее*, – то есть всё с тем
же или меньшим числом (`warning` – это 4).
```

## Диагностика службы, которая не запускается

Кто-то настроил на этом компьютере службу **rapportd**, но с ней что-то не
так. Обычно действуют так:

1. **Что завершилось сбоем?** Выведите список служб со сбоем:

   ```sh
   systemctl --failed
   ```

2. **Посмотрите на состояние.** Часто хватает последних строк:

   ```sh
   systemctl status rapportd
   ```

3. **Прочитайте весь журнал** службы. Почти всегда там написано, в чём
   проблема, – читайте внимательно, слово за словом:

   ```sh
   journalctl -xeu rapportd
   ```

   Сам `systemctl` предлагает именно эту команду, когда запуск не удался:
   `See "systemctl status rapportd.service" and "journalctl -xeu
   rapportd.service" for details.`

4. **Устраните проблему**, например отсутствующий конфигурационный файл или
   опечатку в нём.

5. **Перезапустите и проверьте:**

   ```text
   sudo systemctl restart rapportd
   systemctl status rapportd
   ```

Строка `Main process exited, code=exited, status=1/FAILURE` означает, что
программа сама завершилась с ошибкой. Если написано `status=203/EXEC`,
systemd вообще не смог найти программу – проверьте путь в `ExecStart=`.

```quiz
Служба не запускается, а в журнале написано `status=203/EXEC`. Куда смотреть
в первую очередь?
- [ ] В `/etc/fstab`
- [x] На путь в `ExecStart=` в юнит-файле
- [ ] На приоритет с помощью `journalctl -p err`
- [ ] Никуда – это значит, что программа сама завершилась с ошибкой
---
203/EXEC означает, что systemd вообще не смог найти программу. Программа,
которая запускается, а потом завершается с ошибкой, даёт вместо этого
`status=1/FAILURE`.
```

## Юнит-файл – `systemctl cat`

Чтобы точно увидеть, как запускается служба, прочитайте её юнит-файл:

```sh
systemctl cat minserver
```

```text
# /etc/systemd/system/minserver.service
[Unit]
Description=Minserver web server (practice server)
After=network.target

[Service]
ExecStart=/usr/local/bin/minserver --port 8080
ExecReload=/bin/kill -HUP $MAINPID

[Install]
WantedBy=multi-user.target
```

| Раздел | Содержимое |
|---|---|
| `[Unit]` | Описание и порядок: `After=network.target` = запускать после сети |
| `[Service]` | Как работает программа: `ExecStart=` (команда), `User=`, `Restart=on-failure` … |
| `[Install]` | Что должен делать `enable`: `WantedBy=multi-user.target` |

Если вы изменили юнит-файл, systemd должен загрузить его заново, прежде чем
изменение вступит в силу, – иначе вы получите предупреждение в
`systemctl status`:

```text
sudo systemctl daemon-reload
```

Никогда не редактируйте файлы в `/usr/lib/systemd/system` – они будут
перезаписаны при следующем обновлении пакета. Вместо этого положите свою
версию в `/etc/systemd/system`.

```quiz
Вы хотите изменить то, как запускается служба, поставляемая с пакетом. Как
правильно это сделать?
- [ ] Отредактировать её файл в `/usr/lib/systemd/system` и перезапустить службу
- [x] Положить свою версию в `/etc/systemd/system`, выполнить `sudo systemctl daemon-reload` и перезапустить службу
- [ ] Положить свою версию в `/etc/systemd/system` – systemd сам заметит изменение
- [ ] Отредактировать файл в `/usr/lib/systemd/system` и выполнить для него `sudo systemctl enable`
---
Файлы в `/etc/systemd/system` имеют приоритет и не перезаписываются при
обновлении пакета. `daemon-reload` заставляет systemd заново загрузить
изменённый юнит-файл.
```

## Как называются службы?

systemd везде работает одинаково, но **службы не всегда называются
одинаково** – это зависит от того, как называются пакеты и какие программы
выбрал дистрибутив. В Ubuntu:

| Служба | Имя в Ubuntu |
|---|---|
| SSH-сервер | `ssh` (псевдоним `sshd`) |
| Задания по расписанию (cron) | `cron` |
| Сеть | `NetworkManager` |
| Файрвол | `ufw` (если установлен) |
| Часы | `systemd-timesyncd` |

На самом деле служба SSH называется `ssh.service`. У неё есть псевдоним
`sshd.service`, так что `systemctl status sshd` тоже работает – но в выводе
указано настоящее имя. В других семействах те же службы могут называться
иначе (в Arch и Fedora служба SSH называется `sshd`) – о таких различиях
рассказывает часть о дистрибутивах и пакетах.

Не знаете, как что-то называется? Поищите в списке:

```sh
systemctl list-unit-files | grep ssh
```

```try
systemctl list-unit-files | grep ssh
---
`ssh.service` – настоящий юнит-файл, а `sshd.service` указан как его `alias`.
```

## Перезагрузка компьютера

Действие `enable` проявляется только при перезагрузке компьютера. Это можно
попробовать в симуляторе – он перезагружается мгновенно:

```text
sudo systemctl reboot
```

После перезагрузки работают только включённые службы. С помощью
`journalctl -b -1` вы увидите журнал предыдущей загрузки (и то, как всё
выключалось), а `journalctl --list-boots` показывает все загрузки в
journal.

## Ещё немного о systemd

```sh
hostnamectl
systemd-analyze
systemd-analyze blame
```

`hostnamectl` показывает имя компьютера, операционную систему и ядро (а
переименовать компьютер можно командой
`sudo hostnamectl set-hostname НОВОЕИМЯ`). `systemd-analyze` показывает,
сколько длилась загрузка, а `blame` – какие службы заняли больше всего
времени. Идеально, когда компьютер загружается медленно.
